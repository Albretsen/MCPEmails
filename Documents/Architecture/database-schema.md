# Database Schema Architecture

## Purpose

This document defines the PostgreSQL database schema for MCPEmails — a SaaS platform that exposes user email accounts over the Model Context Protocol (MCP). The schema is hosted on Supabase and must satisfy four competing requirements simultaneously: strict multi-tenant data isolation, low-latency query performance at MCP tool-call frequency, secure storage of sensitive credentials (OAuth tokens, API keys), and auditability of every action performed by an AI agent on behalf of a user.

---

## Design Decisions

**UUID primary keys everywhere.** All tables use `uuid` primary keys generated by `gen_random_uuid()`. This avoids sequential ID enumeration attacks, enables safe cross-environment data migration, and is compatible with Supabase's client-side optimistic inserts.

**`workspace_id` as the multi-tenancy anchor.** Every tenant-scoped table carries a non-nullable `workspace_id` foreign key. Row-Level Security policies (documented separately in `row-level-security.md`) filter exclusively on this column, so the database itself enforces isolation even if application code has a bug.

**`workspaces` as the single tenancy boundary.** The initial product ships one workspace per user, but the schema is designed to allow a user to belong to multiple workspaces in the future (e.g., personal vs. business), or for workspace ownership to transfer. The `workspaces` table owns tenant-level configuration; the `users` table owns identity.

**Soft deletes only where replayability matters.** Email inboxes and API keys are soft-deleted (`deleted_at`) so that the activity log retains foreign-key-linkable history. Tables that exist purely for ephemeral state (e.g., OAuth state nonces) use hard deletes.

**Encrypted-at-rest sensitive columns.** OAuth access tokens, refresh tokens, IMAP/SMTP passwords, and raw API key values are never stored in plaintext. The application layer encrypts these with AES-256-GCM before writing and decrypts on read. Supabase's Vault extension (`pgsodium`) is used for key management.

**`updated_at` trigger on all mutable tables.** A shared `moddatetime` trigger automatically maintains `updated_at` on every `UPDATE`, removing the burden from application code and ensuring the column is always accurate.

**Append-only audit tables.** `activity_log` and `auth_logs` are append-only by application convention; no `UPDATE` or `DELETE` is issued against them except by scheduled archival jobs. RLS policies enforce this.

## Tables

### `users`

Stores Supabase Auth identities. The `id` column mirrors `auth.users.id` so Supabase's built-in JWT subject claim resolves directly to a row.

```sql
CREATE TABLE public.users (
  id            uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  email         text NOT NULL UNIQUE,
  display_name  text,
  avatar_url    text,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);
```

**Constraints and indexes:**

- `UNIQUE (email)` — enforced at the application layer as well, but the database is the source of truth.
- No `workspace_id` here — the join flows through the `workspace_members` join table (see below).

**Notes:**

- Row insertions are triggered by a Supabase Auth hook (`on_auth_user_created`) that copies the new `auth.users` row into `public.users`. This keeps the public schema in sync without requiring application code at sign-up time.
- Deletion of an `auth.users` row cascades here, which in turn cascades to `workspace_members`, which cascades (via the workspace) to all tenant data.

---

### `workspaces`

The top-level tenancy container. One workspace owns all inboxes, API keys, and audit events.

```sql
CREATE TABLE public.workspaces (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  slug          text NOT NULL UNIQUE,       -- URL-safe name, e.g. "acme-corp"
  display_name  text NOT NULL,
  owner_id      uuid NOT NULL REFERENCES public.users(id) ON DELETE RESTRICT,
  plan          text NOT NULL DEFAULT 'free', -- 'free' | 'pro' | 'enterprise'
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);
```

**Constraints and indexes:**

- `UNIQUE (slug)` — used in API paths and MCP server URLs.
- `INDEX (owner_id)` — fast lookup of workspaces owned by a user during login.
- `ON DELETE RESTRICT` on `owner_id` — a workspace cannot be left ownerless; ownership must be transferred before the owner account is deleted.

---

### `workspace_members`

Join table that maps users to workspaces with a role. Enables future multi-member workspaces without schema migration.

```sql
CREATE TABLE public.workspace_members (
  workspace_id  uuid NOT NULL REFERENCES public.workspaces(id) ON DELETE CASCADE,
  user_id       uuid NOT NULL REFERENCES public.users(id) ON DELETE CASCADE,
  role          text NOT NULL DEFAULT 'owner',  -- 'owner' | 'member' | 'viewer'
  joined_at     timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (workspace_id, user_id)
);
```

**Constraints and indexes:**

- Composite primary key on `(workspace_id, user_id)` — prevents duplicate memberships.
- `INDEX (user_id)` — the most common query pattern is "list all workspaces for this user".

---

### `inboxes`

Represents a connected email account. Supports Gmail, Outlook (Microsoft Graph), Fastmail, and generic IMAP/SMTP providers.

```sql
CREATE TABLE public.inboxes (
  id                   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  workspace_id         uuid NOT NULL REFERENCES public.workspaces(id) ON DELETE CASCADE,
  provider             text NOT NULL,          -- 'gmail' | 'outlook' | 'fastmail' | 'imap'
  email_address        text NOT NULL,
  display_name         text,
  -- OAuth providers (Gmail, Outlook)
  oauth_access_token   bytea,                  -- AES-256-GCM encrypted
  oauth_refresh_token  bytea,                  -- AES-256-GCM encrypted
  oauth_token_expires_at  timestamptz,
  oauth_scope          text,
  -- IMAP/SMTP providers (Fastmail, generic)
  imap_host            text,
  imap_port            integer,
  imap_tls             boolean NOT NULL DEFAULT true,
  smtp_host            text,
  smtp_port            integer,
  smtp_tls             boolean NOT NULL DEFAULT true,
  imap_password        bytea,                  -- AES-256-GCM encrypted
  -- Connection state
  status               text NOT NULL DEFAULT 'pending',
                                               -- 'pending' | 'active' | 'error' | 'revoked'
  last_sync_at         timestamptz,
  last_error           text,                   -- human-readable, never includes secrets
  -- Soft delete
  deleted_at           timestamptz,
  created_at           timestamptz NOT NULL DEFAULT now(),
  updated_at           timestamptz NOT NULL DEFAULT now()
);
```

**Constraints and indexes:**

- `INDEX (workspace_id, status)` — the dashboard inbox list filters by workspace and active status.
- `INDEX (workspace_id, provider)` — MCP authentication maps an API key to inboxes filtered by provider.
- `INDEX (oauth_token_expires_at) WHERE status = 'active' AND provider IN ('gmail','outlook')` — partial index used by the token-refresh Edge Function to find expiring tokens efficiently.
- `UNIQUE (workspace_id, email_address) WHERE deleted_at IS NULL` — prevents the same address being connected twice in the same workspace (while allowing re-connection after soft delete).

**Notes on encrypted columns:**

- `oauth_access_token`, `oauth_refresh_token`, and `imap_password` are stored as `bytea` containing the AES-256-GCM ciphertext with a prepended 12-byte IV and 16-byte auth tag. The encryption key lives in Supabase Vault and is never exposed to the application's runtime environment directly — it is passed as a Vault secret reference resolved inside Edge Functions.
- Application code **never** calls `SELECT *` on this table; it always explicitly names columns and requests the encrypted columns only when the token is about to be used.

### `api_keys`

MCP API keys issued to users. Each key carries a set of scopes that limit which MCP tools can be invoked and which inboxes can be accessed.

```sql
CREATE TABLE public.api_keys (
  id                uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  workspace_id      uuid NOT NULL REFERENCES public.workspaces(id) ON DELETE CASCADE,
  created_by        uuid NOT NULL REFERENCES public.users(id) ON DELETE RESTRICT,
  name              text NOT NULL,             -- human label, e.g. "Claude Desktop key"
  key_prefix        text NOT NULL,             -- first 8 chars of the key, shown in UI
  key_hash          text NOT NULL UNIQUE,      -- bcrypt hash of the full key
  scopes            text[] NOT NULL DEFAULT '{}',
                                               -- e.g. {'read:email', 'send:email'}
  inbox_ids         uuid[],                    -- null = all inboxes; array = specific inboxes
  expires_at        timestamptz,               -- null = never
  last_used_at      timestamptz,
  -- Soft delete (revocation)
  deleted_at        timestamptz,
  created_at        timestamptz NOT NULL DEFAULT now(),
  updated_at        timestamptz NOT NULL DEFAULT now()
);
```

**Constraints and indexes:**

- `UNIQUE (key_hash)` — authentication lookups are by hash; the raw key is shown exactly once at creation time and never stored.
- `INDEX (workspace_id) WHERE deleted_at IS NULL` — list active keys per workspace.
- `INDEX (key_prefix)` — used in the dashboard to display partial key identifiers; never used for authentication.

**Key lifecycle:**

1. Application generates a cryptographically random 32-byte key, encodes it as `mcpe_<base58>`.
2. The first 8 characters after the prefix become `key_prefix` (displayed in UI for identification).
3. The full key is bcrypt-hashed (`cost=12`) and stored as `key_hash`. The plaintext is discarded.
4. On MCP authentication, the incoming bearer token is hashed and compared via constant-time comparison against stored hashes.

**Scopes (initial set):**

| Scope | Permitted MCP tools |
|---|---|
| `read:email` | `list_inbox`, `read_email`, `search_email` |
| `send:email` | `send_email`, `reply_to_email`, `forward_email` |
| `manage:drafts` | `create_draft`, `update_draft`, `delete_draft` |
| `manage:folders` | `create_folder`, `move_email`, `delete_email` |

### `oauth_states`

Short-lived nonces used during the OAuth 2.0 authorization code flow for Gmail and Outlook. Entries are deleted after use or after expiry.

```sql
CREATE TABLE public.oauth_states (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  workspace_id  uuid NOT NULL REFERENCES public.workspaces(id) ON DELETE CASCADE,
  user_id       uuid NOT NULL REFERENCES public.users(id) ON DELETE CASCADE,
  provider      text NOT NULL,
  state         text NOT NULL UNIQUE,         -- cryptographically random, 32 bytes base64url
  redirect_uri  text NOT NULL,               -- the redirect_uri sent to the provider
  expires_at    timestamptz NOT NULL DEFAULT (now() + interval '10 minutes'),
  created_at    timestamptz NOT NULL DEFAULT now()
);
```

**Constraints and indexes:**

- `UNIQUE (state)` — the OAuth callback looks up the state value; uniqueness prevents collision.
- `INDEX (expires_at)` — a scheduled cleanup job deletes expired rows; partial index filters efficiently.

**Notes:**

- These rows are hard-deleted on use (after validating the callback) or by a periodic vacuum job for expired rows.
- The `redirect_uri` is stored here and validated exactly (string equality) in the callback handler to prevent OAuth redirect URI manipulation attacks.

### `activity_log`

Append-only record of every MCP tool invocation. Used for auditing, rate-limit enforcement, and the dashboard activity feed.

```sql
CREATE TABLE public.activity_log (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  workspace_id    uuid NOT NULL REFERENCES public.workspaces(id) ON DELETE CASCADE,
  api_key_id      uuid REFERENCES public.api_keys(id) ON DELETE SET NULL,
  inbox_id        uuid REFERENCES public.inboxes(id) ON DELETE SET NULL,
  tool_name       text NOT NULL,              -- e.g. 'read_email', 'send_email'
  status          text NOT NULL,              -- 'success' | 'error' | 'rate_limited'
  error_code      text,
  duration_ms     integer,
  ip_address      inet,
  user_agent      text,
  created_at      timestamptz NOT NULL DEFAULT now()
) PARTITION BY RANGE (created_at);

-- Initial partitions (new partitions created monthly by Edge Function)
CREATE TABLE public.activity_log_2026_05
  PARTITION OF public.activity_log
  FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');

CREATE TABLE public.activity_log_2026_06
  PARTITION OF public.activity_log
  FOR VALUES FROM ('2026-06-01') TO ('2026-07-01');
```

**Constraints and indexes:**

- `INDEX (workspace_id, created_at DESC)` on each partition — the activity feed loads the most recent events per workspace.
- `INDEX (api_key_id, created_at DESC)` — rate-limit enforcement counts recent calls per key.
- `INDEX (tool_name, created_at)` — usage analytics aggregate calls by tool.
- Foreign keys use `ON DELETE SET NULL` so log rows survive inbox or key deletion; `workspace_id` uses `ON DELETE CASCADE` because all tenant data is purged on workspace deletion.

**Partitioning strategy:**

- Range partitioned by `created_at` (monthly). Each new partition is created 7 days before month-end by a scheduled Edge Function.
- Partitions older than 13 months are detached and archived to Supabase Storage as Parquet files before being dropped. This keeps the live table small and queries fast.
- At current scale, a single unpartitioned table would suffice; partitioning is introduced from the start because retrofitting it later requires a full table lock.

### `auth_logs`

Append-only security event log for authentication events: logins, logouts, failed attempts, key revocations, and scope changes.

```sql
CREATE TABLE public.auth_logs (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  workspace_id  uuid REFERENCES public.workspaces(id) ON DELETE SET NULL,
  user_id       uuid REFERENCES public.users(id) ON DELETE SET NULL,
  event_type    text NOT NULL,
                -- 'login_success' | 'login_failure' | 'logout'
                -- | 'key_created' | 'key_revoked' | 'scope_changed'
                -- | 'token_refreshed' | 'token_revoked'
  provider      text,                         -- 'email' | 'google' | 'microsoft'
  ip_address    inet,
  user_agent    text,
  metadata      jsonb,                        -- event-specific extra data (no secrets)
  created_at    timestamptz NOT NULL DEFAULT now()
);
```

**Constraints and indexes:**

- `INDEX (user_id, created_at DESC)` — security review page loads login history per user.
- `INDEX (workspace_id, event_type, created_at DESC)` — workspace-level security dashboards.

**Notes:**

- `metadata` is a free-form JSONB column for event-specific data (e.g., which scopes were added/removed). It must never contain secrets, tokens, or PII beyond what is already in named columns.
- Rows are never updated or deleted by the application. A retention policy archives rows older than 2 years to cold storage.

## Naming Conventions

| Element | Convention | Example |
|---|---|---|
| Tables | `snake_case`, plural nouns | `api_keys`, `activity_log` |
| Columns | `snake_case` | `workspace_id`, `created_at` |
| Primary keys | Always `id uuid` | `id uuid PRIMARY KEY` |
| Foreign keys | `<referenced_table_singular>_id` | `workspace_id`, `user_id` |
| Timestamps | `created_at`, `updated_at`, `deleted_at`, `*_at` suffix | `last_sync_at`, `expires_at` |
| Boolean flags | Affirmative adjective | `imap_tls`, `is_verified` |
| Encrypted columns | No special suffix; documented in schema and ADR | `oauth_access_token` |
| Indexes | `idx_<table>_<columns>` | `idx_inboxes_workspace_id_status` |
| Partial indexes | `idx_<table>_<columns>_<condition_summary>` | `idx_inboxes_token_expires_active` |
| Enum-like text columns | Documented inline via comments; no Postgres `ENUM` type (to allow migrations without table locks) | `status text -- 'pending'\|'active'\|'error'` |

## Security Considerations

**Credential encryption.** OAuth tokens and IMAP passwords are encrypted at the application layer (AES-256-GCM) before they reach the database. Supabase's Transparent Column Encryption (TCE) via `pgsodium` provides an additional layer for these `bytea` columns. Even if an attacker gained direct PostgreSQL access (bypassing RLS), they would see ciphertext, not usable credentials.

**RLS as the last line of defence.** Row-Level Security is enabled on every tenant-scoped table. Policies filter all reads and writes by comparing `workspace_id` to the workspace the current JWT has access to. This is documented in detail in `row-level-security.md`. The database must never be accessed with the `service_role` key from client-facing code.

**Append-only audit tables.** `activity_log` and `auth_logs` use RLS policies that allow `INSERT` but deny `UPDATE` and `DELETE` for all non-service-role roles. This ensures audit trails cannot be tampered with by a compromised application session.

**No plaintext secrets.** The `api_keys` table stores only a bcrypt hash and a display prefix. The plaintext key is generated in memory, shown once to the user, and discarded. If the database is breached, no usable API keys are exposed.

**`oauth_states` expiry.** OAuth state nonces expire after 10 minutes and are single-use. The `redirect_uri` stored with each state is validated by exact string equality in the callback handler, preventing redirect URI manipulation (as required by the OAuth 2.0 security best practices and SSRF mitigations described in `Documents/MCP/security-best-practices.md`).

**Column-level minimisation.** Application queries never use `SELECT *`. Each query lists only the columns it needs, reducing the blast radius of a query injection bug and avoiding accidental exposure of encrypted blobs to logs.

## Performance Considerations

**Composite indexes on `(workspace_id, <filter>)`**. Because RLS already filters by `workspace_id`, every non-trivial query begins with a workspace equality check. Composite indexes always lead with `workspace_id` so the planner can use an index scan rather than a sequential scan of the tenant-filtered rows.

**Partial indexes for hot paths.** The OAuth token refresh job queries only active inboxes with expiring tokens. A partial index on `(oauth_token_expires_at) WHERE status = 'active'` eliminates the full-table overhead.

**Partitioned `activity_log`.** Monthly range partitioning keeps the working set of each query confined to one or two partitions. The MCP rate-limit enforcer (which counts calls in the last 60 seconds per key) only ever touches the current month's partition.

**`SELECT` column projection.** Encrypted `bytea` columns on `inboxes` can be large. Application code never fetches them unless a tool call actually requires the credential. Dashboard list queries select only `id, email_address, display_name, status, last_sync_at`.

**Connection pooling.** Supabase uses PgBouncer in transaction-mode pooling by default. Edge Functions — which are short-lived — benefit directly from this; they acquire a connection for a single transaction and release it. The schema avoids advisory locks and long-running transactions that would hold pool slots.

**`updated_at` via trigger.** Using a trigger (`moddatetime` extension) to maintain `updated_at` removes one round-trip from every update path in application code and guarantees the column is never forgotten.

**Materialized views for analytics (future).** Usage aggregations shown on the workspace dashboard (calls per tool, calls per day) will be served by materialized views refreshed on a 5-minute schedule rather than live aggregates against the partitioned `activity_log`. This is not implemented initially but the schema is designed to support it without structural changes.

## Integration Points

**Supabase Auth → `public.users`**. A database trigger on `auth.users` (managed by Supabase) fires `INSERT INTO public.users` on every new signup. The application layer does not need to create users manually.

**Next.js Server Components / Route Handlers**. Server-side code uses `@supabase/ssr` to create a request-scoped Supabase client whose JWT is resolved to the `public.users` identity and then to the `workspace_members` row. RLS policies derived from this JWT apply automatically to all queries.

**MCP Edge Function**. The MCP server runs as a Supabase Edge Function. On each tool invocation it: (1) extracts the bearer token from the `Authorization` header, (2) bcrypt-compares it against `api_keys.key_hash`, (3) loads the matching inbox credentials from `inboxes`, (4) performs the email operation, and (5) appends a row to `activity_log`. Steps 2–5 run inside a single short transaction.

**Token Refresh Edge Function**. A scheduled Edge Function queries `inboxes WHERE oauth_token_expires_at < now() + interval '10 minutes' AND status = 'active'`, decrypts each token using the Vault key, calls the provider's token endpoint, re-encrypts, and writes back the new token. All writes are transactional; if the provider call fails, the `status` is set to `'error'` and `last_error` is populated.

**Real-time**. The Supabase Realtime channel for the dashboard activity feed subscribes to `INSERT` events on `activity_log` filtered by `workspace_id`. No other table uses Realtime; the cost of maintaining a live subscription is not justified for lower-velocity tables.
