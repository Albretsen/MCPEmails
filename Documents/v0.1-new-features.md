# MCP Emails — v0.1 New Features

> Roadmap for expanding MCP Emails from a read+compose server into a **full mailbox operator**, benchmarked against [tecnologicachile/mail-mcp](https://github.com/tecnologicachile/mail-mcp) (Rust, 30 tools). Every feature below links to where mail-mcp implements it so you can borrow their approach when building the equivalent on your stack (Deno edge function + Supabase + Gmail/Outlook OAuth + IMAP/SMTP).

## Direction (decided)

- **Product vision:** Full mailbox operator — agents can read, organize, file, flag, move, delete, forward, and clean up the inbox like a human assistant. Plus drafts/contacts/scheduling as differentiators mail-mcp lacks.
- **Risk posture:** **Confirmation-gated.** Destructive ops (delete, bulk, folder delete) are allowed but require an explicit `confirm: true` parameter, on top of API-key scopes. This mirrors mail-mcp's double gate (`confirm=true` + `MAIL_IMAP_WRITE_ENABLED`).
- **Provider strategy:** **Best-effort per provider.** Ship each feature where the provider supports it and degrade gracefully; don't block a feature on universal parity. Gmail uses labels (not folders), Outlook/IMAP use folders, IMAP exposes flags directly — surface capabilities per inbox.

## Where you are today

Current tools (`supabase/functions/mcp-server/index.ts`): `list_inboxes`, `list_inbox`, `read_email`, `search_emails`, `send_email`, `reply_to_email`. Scopes `manage:drafts` and `manage:folders` are already reserved in migrations but unused. IMAP/SMTP clients and a MIME parser already exist in the edge function — most new IMAP verbs are thin additions on top of `imap-client.ts`.

## Group A — Flags & state *(v0.1 priority)*

Mark read/unread, star/flag, archive. Low risk, high value — `list_inbox` already reads these flags, so this closes the read/write loop. Best-effort: IMAP uses `\Seen` / `\Flagged` STORE; Gmail/Outlook use their native message-update APIs (Gmail `modify` labels `UNREAD`/`STARRED`, Graph `isRead`/`flag`).

| New tool | Purpose | Provider mapping |
|---|---|---|
| `mark_read` / `mark_unread` | Toggle seen state | IMAP `\Seen`; Gmail remove/add `UNREAD` label; Graph `isRead` |
| `flag_email` / `unflag_email` | Star/flag a message | IMAP `\Flagged`; Gmail `STARRED`; Graph `flag.flagStatus` |
| `archive_email` | Remove from inbox without deleting | IMAP move out of INBOX; Gmail remove `INBOX` label; Graph move to Archive |

**mail-mcp reference:**
- Tool `imap_update_message_flags` — schema/dispatch [`src/server.rs#L338-L357`](https://github.com/tecnologicachile/mail-mcp/blob/HEAD/src/server.rs#L338); implementation `uid_store` [`src/imap.rs#L433`](https://github.com/tecnologicachile/mail-mcp/blob/HEAD/src/imap.rs#L433).
- Flag parsing helper `flags_to_strings` [`src/imap.rs#L394`](https://github.com/tecnologicachile/mail-mcp/blob/HEAD/src/imap.rs#L394) — useful pattern for normalizing IMAP flags into your JSON output.

## Group B — Folder / label operations *(v0.1 priority)*

List/create/rename/delete folders and move/copy messages. Uses your reserved `manage:folders` scope. This is the biggest "operator" gap. Best-effort: model **labels (Gmail)** and **folders (Outlook/IMAP)** behind one tool surface, returning a `type` field so the agent knows which it's working with.

| New tool | Purpose | Provider mapping |
|---|---|---|
| `list_folders` | Enumerate folders/labels with message counts | IMAP `LIST` + `STATUS`; Gmail labels.list; Graph mailFolders |
| `create_folder` | New folder/label | IMAP `CREATE`; Gmail labels.create; Graph create folder |
| `rename_folder` | Rename | IMAP `RENAME`; Gmail labels.patch; Graph update |
| `delete_folder` | Remove folder *(confirm-gated)* | IMAP `DELETE`; Gmail labels.delete; Graph delete |
| `move_email` | Relocate message to a folder/label | IMAP `MOVE`/COPY+expunge; Gmail label swap; Graph move |
| `copy_email` | Copy message into a folder | IMAP `COPY`; Gmail add label; Graph copy |

## Group C — Delete & bulk *(v0.1 priority — destructive tier)*

Confirmation-gated single delete plus bulk move/delete/flag. mail-mcp caps bulk at **500 IDs per call** (`MAX_BULK_IDS`) and requires `confirm: true` for every destructive path — adopt both. Best-effort: prefer "move to Trash" semantics where the provider distinguishes trash from hard-expunge (safer default); only hard-delete when explicitly asked.

| New tool | Purpose | Notes |
|---|---|---|
| `delete_email` | Delete one message *(confirm-gated)* | Default to Trash; `permanent: true` to expunge |
| `bulk_move` | Move up to N messages | Same source folder; cap ~500 |
| `bulk_delete` | Delete up to N messages *(confirm-gated)* | Cap ~500 |
| `bulk_flag` | Flag/mark-read up to N messages | Cap ~500 |
| `search_and_move` / `search_and_delete` | Atomic search→act *(delete confirm-gated)* | Server runs the search to avoid stale IDs |

**mail-mcp reference:**
- Bulk cap constant `MAX_BULK_IDS = 500` — [`src/server.rs#L43`](https://github.com/tecnologicachile/mail-mcp/blob/HEAD/src/server.rs#L43).
- Confirmation-gate pattern (`if !input.confirm { error }`) — single delete [`src/server.rs#L2203`](https://github.com/tecnologicachile/mail-mcp/blob/HEAD/src/server.rs#L2203), bulk delete [`src/server.rs#L2662`](https://github.com/tecnologicachile/mail-mcp/blob/HEAD/src/server.rs#L2662), search_and_delete [`src/server.rs#L2510`](https://github.com/tecnologicachile/mail-mcp/blob/HEAD/src/server.rs#L2510). This `confirm` check is exactly the guardrail you chose — copy the shape.
- `imap_delete_message` — [`src/server.rs#L398`](https://github.com/tecnologicachile/mail-mcp/blob/HEAD/src/server.rs#L398); impl `uid_expunge` [`src/imap.rs#L494`](https://github.com/tecnologicachile/mail-mcp/blob/HEAD/src/imap.rs#L494).

## Group D — Forward *(v0.1 priority)*

Forward an email with the original inlined (and optionally its attachments). Compose-side gap. Best-effort: reuse your existing `send_email` MIME-building path; the only new logic is constructing the forwarded body and re-attaching original parts.

| New tool | Purpose |
|---|---|
| `forward_email` | Forward a message to new recipients, original quoted inline, attachments optional |

**mail-mcp reference:**

## Group E — Drafts *(differentiator — beyond mail-mcp)*

mail-mcp **does not implement drafts** (their roadmap lists it as future). Your `manage:drafts` scope is already reserved, so this is a clean win. Best-effort: Gmail/Graph have first-class draft APIs; for IMAP, a draft is an `APPEND` to the Drafts folder with the `\Draft` flag.

| New tool | Purpose | Provider mapping |
|---|---|---|
| `create_draft` | Save a composed message as a draft | Gmail drafts.create; Graph create message in Drafts; IMAP APPEND to Drafts |
| `update_draft` | Edit an existing draft | Gmail drafts.update; Graph PATCH; IMAP delete+re-append |
| `list_drafts` | List drafts | Native list or IMAP SELECT Drafts |
| `send_draft` | Send a saved draft | Gmail drafts.send; Graph send; IMAP read draft → SMTP send |

**mail-mcp reference (closest analog, not a direct draft tool):**
- `imap_append_message` — appends a raw RFC822 message to any mailbox, the exact mechanic for IMAP drafts: schema [`src/server.rs#L557`](https://github.com/tecnologicachile/mail-mcp/blob/HEAD/src/server.rs#L557); impl `append` [`src/imap.rs#L516`](https://github.com/tecnologicachile/mail-mcp/blob/HEAD/src/imap.rs#L516). Append to `Drafts` with the `\Draft` flag and you have IMAP draft creation.
- Their MIME assembly in `src/mime.rs` is the template for building the RFC822 bytes you'll append.

## Group F — Contacts *(differentiator — beyond mail-mcp)*

Not in mail-mcp. Extract/search contacts from mail history (frequency, last-contacted) and optionally the provider's address book. Needs a new `contacts` table (or derive on the fly from `search_emails` results). Best-effort: Gmail People API and Graph `/contacts` give native address books; IMAP has none, so derive from message headers.

| New tool | Purpose |
|---|---|
| `search_contacts` | Find contacts by name/email across mail history + address book |
| `get_contact` | Frequency, last contacted, recent threads for one address |

**mail-mcp reference:** none — no contact features exist. Build from your own `search_emails` + a derived contacts cache. Consider a `contacts` table keyed by `(workspace_id, inbox_id, email_address)` with counters updated on read/send.

---

## Group G — Scheduling *(differentiator — beyond mail-mcp)*

Not in mail-mcp. Schedule a send for later. Needs a `scheduled_sends` table plus a cron/worker to dispatch. Best-effort: Gmail/Graph have no agent-accessible "send later" you can rely on, so own the queue server-side and dispatch via your existing send path.

| New tool | Purpose |
|---|---|
| `schedule_send` | Queue a message to send at a future time |
| `list_scheduled` | List pending scheduled sends |
| `cancel_scheduled` | Cancel a queued send |

**mail-mcp reference:** none. Implementation is yours: a Supabase table + a scheduled edge function (pg_cron or Vercel cron) that calls the same send routine `send_email` uses.

## Suggested build order

1. **Group A (Flags & state)** — smallest, closes the read/write loop, no new tables.
2. **Group B (Folders/labels)** — unlocks the "operator" story; exercises `manage:folders`.
3. **Group C (Delete & bulk)** — reuses B's move/expunge; add the `confirm` gate pattern once and apply everywhere.
4. **Group D (Forward)** — small addition over `send_email`.
5. **Group E (Drafts)** — differentiator, uses `manage:drafts`; IMAP path = APPEND.
6. **Groups F & G (Contacts, Scheduling)** — require new tables; ship after the operator core is stable.

## Cross-cutting notes

- **Capabilities per inbox:** add a capability matrix to `list_inboxes` output (e.g. `supports: [folders|labels, flags, drafts, ...]`) so agents pick valid actions per provider. mail-mcp does this via `list_all_accounts` [`src/server.rs#L189`](https://github.com/tecnologicachile/mail-mcp/blob/HEAD/src/server.rs#L189).
- **Confirm gate:** standardize one `confirm: boolean` param + a uniform error (`"<op> requires confirm=true"`) across all destructive tools, matching mail-mcp's pattern.
- **Bulk caps:** enforce a hard cap (~500) and return partial-success detail.
- **New scopes:** `manage:drafts` and `manage:folders` exist; you'll want to add `delete:email` (or fold delete under `manage:folders`) and a `manage:contacts` / `schedule:email` scope for F/G.
- **Audit logging:** every new tool should write to `activity_log` like the existing six.
