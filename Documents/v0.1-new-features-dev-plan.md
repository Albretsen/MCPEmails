# MCP Emails — v0.1 Dev Plan (autonomous checklist)

> Companion to [v0.1-new-features.md](./v0.1-new-features.md). Read that first for the product direction (full mailbox operator · confirmation-gated · best-effort per provider) and the mail-mcp feature mapping.

## How to use this checklist

- **Work top-to-bottom.** Tasks are ordered so each one only depends on tasks above it. Pick the first unchecked box, complete it fully, check it, move on.
- **Each task is sized for a single agent run** (~100k–300k context). It names the exact files to touch and the reference code to imitate. Do **not** read all of `index.ts` (~8k lines) — jump to the handler region named in the task.
- **No end-to-end testing is available.** Acceptance is **static**: type-check passes, the tool/route is wired into the existing registry/pattern, scopes + confirm gates are present, and the code mirrors an existing working handler. Verify by reading the code you wrote against the referenced pattern, not by running the mailbox.
- **Verification gates** (run what applies):
  - Edge function (Deno): `deno check supabase/functions/mcp-server/index.ts`
  - Web app: `npm run build -w apps/web` and `npm run lint -w apps/web`
  - DB: migration file is present and re-runnable (idempotent `IF NOT EXISTS` / guarded).
- **Deploy is out of scope per task.** Leave deploying (`npx supabase functions deploy mcp-server --project-ref swvaxorwumispmjaaszb --no-verify-jwt`) to the human unless told otherwise.

## Reference repos

- **Our repo (existing patterns to imitate):** https://github.com/Albretsen/MCPEmails
  - MCP server: `supabase/functions/mcp-server/index.ts` — tool registry `TOOL_REGISTRY` (~L968–1329), handlers `executeListInbox` (~L2986), `executeReadEmail` (~L4089), `executeSendEmail` (~L6184), `executeReplyToEmail` (~L5813), `executeSearchEmails` (~L7068), `executeListInboxes` (~L1482).

  - Existing provider/feature matrix doc: `Documents/provider-support.md`.
- **Inspiration repo (mail-mcp, Rust):** https://github.com/tecnologicachile/mail-mcp — per-task links below.

Whenever a task adds a tool, copy the shape of an **existing** tool end-to-end: registry entry → scope check → handler → per-provider dispatch → `activity_log` write → JSON-RPC result. Consistency with the existing six tools is itself an acceptance criterion.
