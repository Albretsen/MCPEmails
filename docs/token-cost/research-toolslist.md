# `tools/list` byte accounting and compression plan

Measured 2026-08-19 against `supabase/functions/mcp-server/index.ts` at the current
worktree HEAD. Raw payload saved to `docs/token-cost/baseline-tools-list.json`.

## 0. Headline

| metric | value |
|---|---|
| wire bytes, whole JSON-RPC frame | **55,494 B** |
| wire bytes, `result.tools` array | **55,450 B** |
| tokens (real tokenizer, cl100k_base) | **12,231** |
| tokens (the bytes/3.7 rule of thumb) | 14,998 (overestimates by 23%) |
| real bytes-per-token for this payload | **4.53** |
| tools listed | **16** (not 9) |

**The 28,000-character figure in the brief is wrong by roughly 2x.** The real
payload is 55,450 bytes. Two things were probably missed when 28,000 was
estimated:

1. There are **16** tools on the wire, not 9. `TOOL_REGISTRY`
   (`index.ts:4688-4699`) has ten mail tools (`signature` is the forgotten
   tenth), and then two loops at `index.ts:4715-4719` and `index.ts:4740-4742`
   append six more: `approval_review`, `approval_decide`, `approval_update`,
   `approval_schedule`, `bulk_execute`, `bulk_cancel`. Those six cost 5,262 B.
2. The `allOf` action-gating rules generated by `buildConsolidatedTool`
   (`index.ts:4644-4659`) add 13,822 B that never appears in the source as
   literal text, so a source-reading estimate misses it entirely.

Coincidentally, dropping the six app-only tools *and* the `allOf` blocks lands
at about 28 KB, which is probably where the old number came from.

## 2. How the payload was extracted

Not hand-counted and not from prose. `deno` is on this machine, so the real
module was executed:

1. Copied `supabase/functions/mcp-server/` to a scratchpad, replaced the single
   `Deno.serve(handleRequest);` line (`index.ts:21386`) with a no-op, and
   appended `export { TOOL_REGISTRY, serializeToolForList, isToolAuthorized }`.
2. Ran it with dummy `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` /
   `ENCRYPTION_KEY` env vars (the module builds a Supabase client at load).
3. Applied the exact production path: `TOOL_REGISTRY.filter(isToolAuthorized)`
   with all eight scopes, then `.map(serializeToolForList)`, then
   `JSON.stringify`. This is byte-identical to what `handleToolsList` returns
   for an all-scope key on an inbox that has not opted into bulk previews.
4. Tokenized with python `tiktoken` `cl100k_base` in a venv. That is a real
   tokenizer, though it is GPT's, not Claude's; treat it as within a few percent.
5. Cross-checked the byte count with the pre-existing
   `docs/token-cost/measure.mjs` from the sibling effort: 55,494 B wire. Agrees.

No network calls were made and no tool was invoked.

Payload variants measured:

| variant | tools | bytes |
|---|---|---|
| A: all-scope key, no bulk-plan opt-in (the common case, and what is saved) | 16 | 55,450 |
| C: only the ten documented mail tools | 10 | 50,142 |

A key with narrower scopes sees less, because `isToolAuthorized`
(`index.ts:2044-2052`) filters, but every consolidated tool's `requiredScope` is
the scope of its *first* action, so nearly any real key sees nearly everything.

## 5. Identified waste

### 5.1 `allOf` action rules: 13,822 B (24.9%), the single biggest lever

`buildConsolidatedTool` (`index.ts:4644-4659`) emits, for every action, an
`if/then` rule that lists every property the action does *not* accept. With 27
properties and 7 actions on `email_read`, this is quadratic: 4,332 B on that one
tool. A representative fragment from `folder` (the smallest consolidated tool,
still 682 B of rules):

```json
{"if":{"properties":{"action":{"const":"rename"}},"required":["action"]},
 "then":{"required":["folder_id","new_name"],
         "not":{"anyOf":[{"required":["name"]}]}}}
```

This is machine-validation grammar. It is repeated 35 times across the payload
and every repetition restates `{"required":["action"]}` and the same property
names. It carries genuine information the model needs (which arguments belong to
which action) but encodes it in the most expensive possible form: the same fact
in a compact prose map costs roughly 150-400 B per tool instead of 700-4,300.

**Load-bearing caveat:** the server validates against the *same* object it
emits. `index.ts:4843-4844` walks `schema.allOf`, and the comment at
`index.ts:4762-4767` is explicit that this exists because clients cannot be
trusted to validate. So `allOf` cannot simply be deleted. It must be *decoupled*:
keep a full internal schema for validation, emit a slimmer public one. That is a
real code change in `buildConsolidatedTool`, not a text edit.

### 5.2 Verbatim duplicated property descriptions: 6,874 B of pure duplication

Identical description strings repeated across tools. Top offenders:

| description | copies | bytes each | duplicate waste | where |
|---|---|---|---|---|
| `inbox_id` | 8 | 337 | **2,359** | `INBOX_ID_PROPERTY`, `index.ts:2092-2101` |
| `inbox` | 8 | 113 | 791 | `INBOX_PROPERTY`, `index.ts:2103-2109` |
| `action` selector | 8 | 70 | 490 | `buildConsolidatedTool`, `index.ts:4610-4611` |
| `idempotency_key` | 3 | 226 | 452 | `IDEMPOTENCY_KEY_PROPERTY`, `index.ts:2131-2140` |
| `query` (raw escape hatch) | 3 | 141 | 282 | `STRUCTURED_SEARCH_PROPERTIES` |
| `include_signature` | 2 | 212 | 212 | `INCLUDE_SIGNATURE_PROPERTY`, `index.ts:2116-2123` |
| the 12 structured search fields | 3 each | 62-98 | ~1,400 combined | `index.ts:2061-2084` |
| `approval_id` | 4 | 70 | 210 | `mcp-app-approvals.ts` |

The `inbox_id` text alone, quoted from `index.ts:2094-2099` (dashes normalized):

> "UUID of the inbox to use. Optional when the API key has access to exactly one
> inbox (it is auto-selected). Alternatively pass `inbox` with an email address.
> If you don't know the inbox_id and several are accessible, just omit it, the
> response then lists every inbox with its inbox_id so you can retry (calling
> inbox_list does the same)."

337 B, paid nine times (eight consolidated tools plus a *different* 397 B variant
on `contact_search` at `index.ts:3518-3528`). That is 3,093 B for one idea.
The retry-on-ambiguity behaviour needs to be stated once, and it is arguably
better stated in the error response the model actually receives (which already
does this, per the project's fresh-connect fix) than in eight schemas.

The full structured search block (`from`, `to`, `cc`, `subject`, `body`, `text`,
`unread`, `has_attachment`, `flagged`, `since`, `before`, `query`) is emitted
three times: on `email_read`, `email_organize` (for `search_and_move`), and
`email_delete` (for `search_and_delete`). Two of those three copies are
duplicates, costing about 1,400 B.

### 5.3 Enums documented twice: every consolidated tool

Every single `action` enum is also spelled out in the tool description. All 8
tools, 35 of 35 action values restated. `email_read`'s 852 B description
enumerates `'list'`, `'read'`, `'read_batch'`, `'search'`, `'attachment'`,
`'extract'`, `'original'`, and the enum lists exactly the same seven. Same for
`email_organize.flag_action` (`['read','unread','flag','unflag']`, all four
restated), `signature.signature_reply_mode`, `inbox_list.provider` ("One of:
gmail, outlook, fastmail, imap" next to the identical enum), and
`approval_decide.decision`.

The prose is not pure waste, because it adds the *meaning* of each action, which
the bare enum does not. But the naming is largely self-documenting and the prose
gloss should be one clause per action, not a paragraph.

### 5.4 `default` restated in prose: 12 properties

Twelve properties carry both a `default` keyword and a description ending in
"Defaults to X": `inbox_list.include_capabilities`, `email_read.limit`,
`email_read.folder`, `email_read.mark_as_read`, `email_read.include_folders`,
`email_compose.include_signature`, `email_compose.include_attachments`,
`draft.limit`, `draft.include_signature`, `draft.reply_all`, `schedule.limit`,
`contact_search.limit`. Small individually (roughly 15-20 B each, ~200 B total),
but free to fix.

Note `draft.limit`'s description is literally "Maximum number of drafts to
return. Defaults to 20." next to `"default":20,"maximum":...`. The whole
description is redundant with the property name plus the keyword.

### 5.5 Verbose prose that could be halved

The three longest descriptions and what they are doing:

- `email_read.include_attachments`, 610 B (`index.ts` around 2270). Explains the
  10 MB budget, the 2 MB inlining threshold, the metadata-always rule, and the
  recommended workflow. **This is genuinely load-bearing** and cutting it will
  cost retries. Compress carefully, do not delete.
- `contact_search` tool description, 824 B (`index.ts:3492-3505`). Repeats the
  "omit inbox_id for cross-inbox questions" guidance that is *also* the bulk of
  `contact_search.inbox_id`'s 397 B description. About 250 B of straight
  self-duplication inside one tool.
- `email_read` tool description, 852 B. Roughly 300 B of it is the pagination
  lecture: inspect `has_more`, call again with `next_offset`, "Only has_more:
  false means the end has been reached." Worth keeping in some form (this is a
  known real failure mode), but it belongs in the tool *result* alongside
  `has_more`, not in every conversation's preamble.

### 5.6 `annotations.title` duplicates the top-level `title`: 444 B

`serializeToolForList` emits both `title` and `annotations.title`
(`mcp-app-resources.ts:296-304`), and `buildConsolidatedTool` sets
`annotations.title = spec.title` (`index.ts:4675`). Every tool therefore carries
its title twice, verbatim. 444 B, zero risk to remove: MCP's `annotations.title`
is the legacy location and top-level `title` is the current one.

### 5.7 `outputSchema`: 1,430 B, only on 2 of 16 tools

`inbox_list` 961 B and `contact_search` 469 B. The 14 consolidated and app tools
have none, because `buildConsolidatedTool` never sets one and the attach loop at
`index.ts:4378-4390` only runs over `LEGACY_TOOLS`.

This is a real cost but a small one (2.6%), and it is also *inconsistent*: the
comment at `index.ts:1623` notes `outputSchema` participates in how a cap
rejection is interpreted. My recommendation is to leave `outputSchema` alone.
It is the wrong 1.4 KB to fight over, and removing it makes the surface less
uniform rather than more.

### 5.8 `_meta`: 630 B, keep

`{"ui":{"resourceUri":"ui://mcpemails/review-card.html"}}` on three mail tools
plus the app-only six. Required for MCP Apps. Not waste.

### 5.9 The six app-only tools: 5,262 B (9.5%)

`approval_*` and `bulk_*` are listed unconditionally and carry
`visibility: ["app"]`. Per the project's own finding (documented at
`index.ts:2019-2025` and in the MCP Apps notes), `visibility` is a host UI hint
and not a boundary. So these 5,262 B are paid on every conversation to expose
tools the model is meant not to pick. This is the largest single *removable*
block, but removing them breaks the MCP Apps flow, so it needs the app team's
sign-off rather than a schema edit.

## 6. Declared vs. actually-read parameters

Every one of the 56 distinct declared property names is read by a handler. There
are no dead parameters and no used-but-undeclared ones. Specifically verified:

- The 12 structured search fields are all consumed by `buildNormalizedSearch`
  (`index.ts:12792-12849`), including `since`/`before` (parsed via
  `parseIsoDate`), `has_attachment`, `flagged`, `unread`, and the `query` raw
  escape hatch.
- `flag_action` looks unread in `index.ts` only because it is a rename: the
  consolidated spec maps `email_flag`'s own `action` to `flag_action`
  (`index.ts:4483`) and reverses it before dispatch (`index.ts:20305-20316`).
- `decision`, `note`, `body_text`, `body_html` read in
  `mcp-app-approvals.ts:912`, `:949`, `:1058-1059`.
- `plan_id` read in `mcp-app-bulk.ts`.

So there is **no free win from dead schema**. Every byte in the payload is
attached to something real; the savings all have to come from saying the same
things more briefly, or from moving them out of `tools/list`.

One structural oddity worth noting, not a byte issue: `requiredScope` on a
consolidated tool is the scope of whichever action happens to be listed first
(`index.ts:4617`), with the rest folded into `altScopes`. That means scope-based
filtering barely reduces the payload for real keys.

## 7. Compression plan

Each step was simulated programmatically against the real payload, so the byte
figures below are measured, not estimated.

| # | change | bytes after | saved | cumulative | risk |
|---|---|---|---|---|---|
| baseline | | 55,450 | | | |
| T1 | replace emitted `allOf` with a compact `action -> args` map in the `action` description; keep the full schema internally for validation | 43,926 | **11,524** | 21% | medium (code change) |
| T2 | rewrite the 4 shared boilerplate property descriptions (`inbox_id`, `inbox`, `idempotency_key`, `include_signature`) | 40,541 | **3,385** | 27% | low |
| T3 | drop `annotations.title` | 40,097 | 444 | 28% | none |
| T4 | rewrite remaining property descriptions to about 110 chars | 35,393 | **4,704** | 36% | medium, see flags |
| T5 | rewrite tool descriptions to about 320 chars | 33,105 | **2,288** | 40% | medium, see flags |
| T6 | *optional*: drop `outputSchema` | 31,643 | 1,462 | 43% | not recommended |
| T7 | *optional*: stop listing the 6 app-only tools | 28,054 | 5,051 | 49% | needs MCP Apps sign-off |

**Recommended target: 33,000 bytes / about 7,300 tokens (T1 through T5).**
That is a 40% cut, 4,900 tokens saved per conversation, with no behavioural
change and no tool removed. T7 on top would reach 28,000 B / 6,400 tokens if the
app team agrees.

### T1 in detail (highest value, do this first)

Change `buildConsolidatedTool` to build two schemas from the same source of
truth: a `validationSchema` retained in the registry entry for
`index.ts:4843`'s validator, and a leaner `inputSchema` for the wire. The wire
version keeps `type`, `properties`, `required:["action"]`,
`additionalProperties:false`, and folds the action-to-argument mapping into the
`action` property description, e.g. for `folder`:

> "Operation to run. Args per action (\*=required): list: inbox, inbox_id;
> create: \*name | inbox, inbox_id; rename: \*folder_id, \*new_name | inbox,
> inbox_id; delete: \*folder_id | inbox, inbox_id"

This preserves every fact the `allOf` block encodes, in a form the model reads
more reliably than nested `not/anyOf`. Server-side rejection of a wrong-shaped
call is unchanged because validation still runs against the full schema.

### Things that must NOT be cut

These are the places where a shorter description would plausibly produce a wrong
call and a retry that costs more than the words saved:

1. **`email_read.include_attachments`, the 2 MB inlining threshold and the
   `attachment_index` workflow.** This is the only place the model learns that
   large attachments come back as metadata with a note, and that the correct
   move is `action: attachment` by index. Cutting it produces a model that sets
   `include_attachments: true`, gets truncated data, and retries. Compress to
   roughly 300 B, do not go below.
2. **`email_read` pagination (`has_more` / `next_offset`).** Keep a one-sentence
   form ("Paginated: if has_more, re-call with next_offset."). The full lecture
   can move to the tool result.
3. **`contact_search`'s "omit inbox_id for cross-inbox questions".** Non-obvious
   and inverted relative to every other tool, where omitting inbox_id is the
   lazy path. Keep it in exactly one place, the tool description, and cut it
   from the `inbox_id` property description (saves about 250 B and removes the
   contradiction with the shared `inbox_id` text).
4. **`email_organize` copy-vs-move provider limits** ("IMAP/Outlook/Fastmail
   only"). Only place the constraint appears.
5. **`idempotency_key`'s "a reused key with different arguments is rejected".**
   The rejection is real and the model cannot infer it. Keep the clause, drop
   the rest.
6. **`email_read.folder` case-sensitivity and the `[Gmail]/Spam` example.**
   The example is worth its bytes.
7. **`flagged` / `has_attachment` "ignored on provider X" notes.** These prevent
   the model from believing a filter was applied. Compress to
   "not on Outlook" / "not on IMAP", keep the fact.

Conversely, these are safe to cut hard: the `inbox_id` retry paragraph (the
error path already tells the model), every "Defaults to N" restatement, the
`draft.limit` / `schedule.limit` / `contact_search.limit` descriptions entirely,
`annotations.title`, and the prose restatement of each `action` enum value where
the value name is self-explanatory (`list`, `create`, `delete`, `send`).

## 8. Interaction with a read/write tool split

If the consolidated action tools are split into separate read and write tools,
the tool count rises and some of these savings change sign.

**Survives the split unchanged (about 8,500 B):**

- T2 shared boilerplate rewrites. `inbox_id` / `inbox` are duplicated *more*
  after a split, not less, so this saving grows. Best done as a shared constant
  edit at `index.ts:2092-2140` either way.
- T3 `annotations.title`. Scales with tool count, so it also grows.
- T4 property description rewrites. Fully portable, and more valuable after a
  split because the same properties recur on more tools.
- T5 tool description rewrites. Portable in substance, though each new tool
  needs its own description written to the same budget.
- T7 app-only tools. Independent of the split entirely.

**Depends on the consolidated shape (about 11,500 B, T1):**

The entire `allOf` saving exists only because consolidated tools exist. A split
deletes `allOf` outright, since each tool has one fixed argument shape. So T1's
11,524 B disappears as a *problem*, but it also disappears as a *saving you can
claim twice*.

**The split's own cost, which needs measuring separately:** splitting multiplies
the per-tool fixed overhead (name, title, description, annotations, and the
repeated `inbox_id`/`inbox` pair, currently about 560 B of fixed cost per tool)
across a larger tool count. Today's 35 actions across 8 consolidated tools would
become up to 35 tools. At today's per-tool overhead that is roughly 20,000 B of
new fixed cost, which would more than eat the 11,500 B that `allOf` gives back.

**Recommendation for coordination:** do T2, T3, T4, T5 first. They are worth
about 10,800 B, are pure text edits, and are correct under either architecture.
Hold T1 until the split decision is made, because if the split lands, T1 is moot,
and if it does not, T1 is the biggest single win available.

## 9. Reproducing these numbers

```
# baseline payload
docs/token-cost/baseline-tools-list.json

# byte/token check with the sibling effort's tool
node docs/token-cost/measure.mjs docs/token-cost/baseline-tools-list.json
```

To regenerate the payload after a change, copy the `mcp-server` directory to a
scratch dir, no-op the trailing `Deno.serve(handleRequest);`, append
`export { TOOL_REGISTRY, serializeToolForList, isToolAuthorized };`, and run the
filter-and-serialize pipeline described in section 2 with dummy env vars.
